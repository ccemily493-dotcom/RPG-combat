## 2. Architecture added

The new `resolveSessionStep` orchestrates the existing authoritative `resolveTurn` resolver:

`immutable snapshot → temporal start → opportunity triggers → DAG eligibility → resolveTurn → strategic consequences → temporal end → bounded history → immutable next snapshot`

The runtime adds:

- explicit `TURN_START`, `PRE_ACTION`, `ACTION_RESOLUTION`, `POST_ACTION`, and `TURN_END` phases;
- cooldown, scheduled-effect, recovery-hook, duration, opportunity, relation, history, and session-state contracts;
- deterministic Strategy DAG validation/scheduling with stable strategy/node ordering;
- ordinary-action, opposed-contest, declarative-condition, and normalized-state-setup node resolver classes;
- deterministic dependency branching and declared failure policies;
- session-level trace, replay metadata, snapshot sequence, and configured termination;
- no duplicated attack, defense, damage, reaction, batching, merge, or transaction formulas.

`resolveEncounter` and `resolveTurn` remain available and mechanically authoritative. No compatibility migration is required except using `ruleset_version: "0.3"` for 0.3 schemas.

## 6. Temporal-state implementation

Temporal state is a validated immutable snapshot component containing phase, scheduled effects, relations, opportunities, recovery hooks, bounded mechanical history, and session metadata. Stable IDs are enforced across temporal collections. Nested scheduled/opportunity payload references are checked before execution.

Previous-turn state now exposes normalized strategy transitions and temporal events without duplicating the complete session history.

## 7. Duration/cooldown behavior

Supported duration units are `TURN`, `PHASE`, `ACTION`, `REACTION_WINDOW`, `UNTIL_TRIGGERED`, `UNTIL_CONDITION`, and `PERMANENT`.

- New turn-duration state does not decrement in its creation turn.
- Phase duration progresses after its named phase.
- Action/reaction-window duration progresses by normalized event count.
- Triggered/conditional duration expires only on its declared trigger/predicate.
- Remaining values are schema-bounded and runtime-clamped against negatives.

Cooldowns use explicit keys, duration, `TURN` units, and `ON_USE`. They progress at `TURN_START`; unavailable direct actions fail before combat commit, while unavailable strategy actions remain pending until eligible.

## 8. Recovery behavior

Action and reaction availability restore to each character's declared capacity at `TURN_START`. Resources and stability do not regenerate implicitly. Explicit recovery hooks are stable-ID ordered, target a declared character/resource or capacity, and clamp to configured maximums.

## 9. Strategy DAG implementation

The formal schema includes stable strategy/node IDs, owner, state, nodes, dependency mode, typed dependencies, declarative conditions, failure policy, fallbacks, completion rule, normalized mechanical payloads, and metadata.

Graphs are acyclic in v0.3. Duplicate IDs, missing dependencies/fallbacks, invalid owners/targets, missing typed payloads, and cycles fail before commit. One newly eligible dependency layer executes per session step; newly unlocked nodes wait for the next step.

There is no `strategyScore`, `strategySuccess`, `tacticalPower`, or `planQuality` mechanic.

## 10. Strategic primitive implementation

The normalized registry covers `FEINT`, `DISTRACTION`, `AMBUSH`, `FLANK`, `BLIND_SPOT`, `BAIT`, `TRAP`, `COVER`, `REPOSITION`, `INTERRUPT_SETUP`, `COUNTER_SETUP`, `ISOLATE`, `RESOURCE_DENIAL`, `AREA_DENIAL`, and `ESCAPE_SETUP`.

Every primitive declares requirements, relevant mechanical inputs, possible target state, world hooks, character hooks, duration contract, outputs, and counterconditions. Resolver classes are deliberately distinct:

- FEINT/DISTRACTION/AMBUSH use different opposed stat terms.
- REPOSITION/INTERRUPT_SETUP require normalized ordinary action/reaction mechanics.
- FLANK/BLIND_SPOT/ISOLATE require declarative state/geometry conditions.
- BAIT/TRAP/COVER/COUNTER_SETUP/RESOURCE_DENIAL/AREA_DENIAL/ESCAPE_SETUP create only declared normalized state/effects.

No primitive guarantees a later hit or bypasses the ordinary resolver.

## 11. Branching/failure-policy results

Dependencies support `ON_SUCCESS`, `ON_FAILURE`, `ON_COMPLETION`, `ALL_OF`, and `ANY_OF`. Failure policies support `CONTINUE`, `CANCEL_DEPENDENTS`, `CANCEL_BRANCH`, `CANCEL_STRATEGY`, and `ACTIVATE_FALLBACK`.

Scenario F deterministically selected the success branch for its true condition and the failure branch for its false condition; opposite branches became `BLOCKED`. Scenario E's failed distraction applied `CANCEL_BRANCH`, cancelling reposition and attack without creating an advantage.

## 19. Specification ambiguities discovered

The following missing lifecycle rules were resolved with explicit conservative configuration and documented in `open-decisions.md`:

- whether newly created turn durations decrement immediately (no);
- when phase durations advance (after their named phase);
- whether action duration counts turns or normalized action events (events);
- when cooldowns advance and become available (`TURN_START`, zero boundary);
- whether newly unlocked DAG nodes run immediately (no; next session step);
- how partial primitive outcomes affect dependencies (provisionally count as success);
- how overall strategy completion is summarized (provisional any-success after all terminal unless cancelled);
- whether preparation reserves cross-turn resources (not by default; trigger-time reservation remains authoritative).

## 20. Suspicious provisional values

- Primitive opposed-contest weights and the 0/10 failure/partial/success bands have deterministic coverage but no playtest calibration.
- The fixture node success rate is intentionally scenario-driven and must not be treated as a target.
- One DAG layer per session step may be too conservative for zero-time conditions/state transitions.
- Session orchestration is validation-heavy: scheduler/temporal overhead is larger than the empty-turn resolver itself, although still about 4.6–5.3 ms/turn in the no-strategy/linear/branching cases.
- Accuracy remains concentrated in a single band for several specialized cohorts, as explicitly accepted for v0.3.
- Weighted-defense p05 remains 15.78%, close to the poor/weak diagnostic boundary, as explicitly accepted.

## 21. Remaining core limitations

- Cooldown units are TURN-only in v0.3.
- Prepared opportunities reserve resources at trigger time; cross-turn locked reservations are not modeled.
- DAGs cannot contain controlled loops and execute at most one newly unlocked dependency layer per step.
- Geometry remains minimal: no pathfinding, continuous event clock, collision solver, or full line-of-effect physics.
- Stateful status batching remains individual unless a future registry explicitly defines safe aggregate semantics.
- Mechanical history is bounded and in-memory; no durable event-log/network protocol exists.
- Primitive registries accept normalized mechanics only; there is no semantic guessing, natural-language strategy parser, tactical AI, Ability Parser, LLM, or universe module.
